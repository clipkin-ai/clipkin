# Directing screen demonstrations

Use this page when a website, app, terminal, editor or any other screen is part of what the viewer has to
understand. A screen in a video does one of three jobs: it documents a real state, it shows an action and
its consequence, or it stages an explanation of a relationship. Work out which job this passage needs
before choosing material or treatment.

## Choose the evidence the claim needs

| Material | What it gives the viewer |
| --- | --- |
| Screenshot | Wording, layout or a specific result, available to read |
| Recording | A real interaction and the interface's actual response |
| Authored component | An isolated concept, a choreographed example, or labels and states that stay editable |

These can share a passage. A real product recording can establish the behavior while surrounding graphics
point out what to notice. A still can also drift under a moving viewport to guide the eye across what it
contains; that motion is a view of the still, not a recorded interaction, and should not be presented as
one.

Decide whether the screen is evidence or illustration:

- **Evidence.** If the claim *is* the precise wording, data or behavior, show material that proves it, and
  record in the project where that material came from.
- **Illustration.** If the screen represents an idea, design the made-up states and actions so that the
  idea is what the viewer takes away.

A film can switch between the two as long as each one's role in the argument stays clear. A behind-the-scenes
film once did exactly this: genuine Studio capture proved the interface works, and a built scene with a chat
box and a moving pointer illustrated a request becoming an attached reference. Those different jobs decided which
material each part used.

## Stage the useful view

Show the part of the screen that carries the fact or the action. The viewer may need the full interface
first to get oriented, then a closer view to read a control or catch a change. Crops, zooms, cursors and
highlights should steer attention while leaving enough context to tell *where* the action happened. Judge
type and controls at the delivered size: a crisp full-resolution capture can turn illegible once it is
shrunk into a phone-sized inset.

Give each interaction a readable before and after. Useful states can include the target, the action, the
visible response and enough time for the result to sink in. An edit may open on the result and then go
back to the cause; what matters is what the viewer can infer.

Be precise about what moves when the content scrolls. Moving the page or an inner list says something
different from moving the viewport, the device or the entire screen card. A real recording runs at the
interface's own pace; an authored demonstration can put its meaningful changes on the work's semantic
events.

The surroundings of the screen are a directing choice too:

| Surround | Effect |
| --- | --- |
| Bare crop | Gives the interface authority and room to be read |
| Photographed device | Places it in a person's world |
| Graphic frame | Ties it to the film's visual language |

Whatever you choose, keep the actual screen readable while deciding what the presenter, Caption and other
graphics add beside it. [Graphic composition](graphic-compositions.md) owns that shared hierarchy, and
[motion graphics](motion-graphics.md) owns animation around or inside an authored demonstration.

How to realize each choice: [Browser capture](../../production/browser-capture.md) owns saving a real page
or recording it, playback and cropping of that capture are in
[Media presentation](../../production/visual-clips.md), and an editable screen scene is built through
[component design](../../production/component-design.md). Pick whichever
serves this passage's screen role.
